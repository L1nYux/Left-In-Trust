# 算力回廊项目推进流程与 AI 提示词

编写日期：2026年10月22日。

本文根据项目内《总览.docx》《玩法.docx》、角色性格索引、Muse设定、《性格审阅与轻喜剧调整建议》及两轮修改意见编写。用于从当前设定阶段推进到可试玩的 PC Demo。以下范围、顺序、时间和验收门槛均为推进建议，不代表已经修改原设定或获得试玩验证。

## 当前判断与下一步

项目已经具备明确题材、16名角色的设定资料、部分美术参考和较完整的玩法构想。本次检查未发现游戏程序工程；`_build` 主要是文档加工资料，不能作为游戏原型已完成的依据。

接下来优先完成一场能反复玩、能解释胜负原因的战斗，再串成一段有招募和构筑变化的流程。建议保留16名角色作为长期内容目标，首轮制作集中在3名角色。

推进顺序：统一规则和范围 → 写出可执行战斗规格 → 制作单场战斗原型 → 验证小队与差异化机制 → 串通肉鸽流程 → 制作展示内容 → 试玩和平衡 → 打包Demo。

每阶段都应交付可检查的文件、数据或可运行版本。前一阶段验收未通过时，先修当前问题，避免继续堆内容。

## 先划清三个版本

| 版本 | 建议范围 | 主要要回答的问题 |
| --- | --- | --- |
| 战斗原型 | 1名角色、1个固定身份、12—16种卡、3种普通敌人模板、1场固定测试战斗，使用占位美术 | 花token打牌、保留token承伤、窗口与缓存是否形成有用的选择？ |
| 内部流程版 | 3名角色、2个身份、1章约6—8个实际经过的节点、1个Boss、一次战后招募；支持在现有3人中安排上场与离线 | 角色组合、选路、奖励与招募能否形成连续体验？ |
| 对外Demo候选 | 3名角色、2个身份、2个短章、约30—40种卡、约6种普通敌人模板、2种精英、2个Boss、少量事件与装备，目标约20—35分钟 | 玩家能否独立理解，并愿意再试一个阵容或构筑？ |

节点数指玩家一条路线实际经过的节点数，不是整张分支地图的节点总数。时长是待实测目标。两章Demo在第二个Boss后结束，这是演示范围的裁剪，不等于把完整版本的六章规则改成两章。

首发候选角色建议为GPT、Claude、DeepSeek：分别验证通才输出、保护公共资源、减费与蓄力。DeepSeek首轮仅做女仆形态，肥鲸形态和GPT进化放到后续扩展；长期保留原设定方向。角色组合可调整，但应覆盖不同玩法职责，并保证每人都有单人开局手段。

协议值、完整提示词链、全角色进化、六章内容、全部身份成长、大量harness、配音、联机和移动端适配均暂缓。先保留harness的数据扩展位置，后期只为Demo实际使用的角色制作少量装备。

## 必须先处理的规则问题

| 问题 | 现有资料中的依据 | 建议处理 |
| --- | --- | --- |
| 战间恢复与休息 | 每场战斗恢复到初始token；休息节点又用于回血 | 原型先沿用每战回满，战间休息暂只做升级或删卡；如果未来要战间损耗，再作为规则变更对照测试 |
| 归零判负与救场 | token归零立即失败；学生身份却允许归零后再打一张0费卡 | 原型优先保持立即失败；学生例外先暂缓，另列“致命结算前救场”的备选方案，不悄悄实现两套规则 |
| 提示词窗口的双重含义 | 载入手牌占容量；打牌又增加窗口占用；满容量性能下降 | 明确手牌载入容量与本回合已执行的上下文负荷如何关联，用两个数值示例走通；避免开局载满即过载 |
| 卡牌的生命周期 | 部分段落说buff进缓存，另一些说所有已打出卡进缓存 | 写清每类卡的去向、未使用手牌去向、牌库耗尽行为、遗忘与离线区是否独立，以及如何恢复；不能凭程序习惯套传统弃牌循环 |
| 行动与额外操作 | 每人每回合行动一次，另有检索、压缩、离线调用、身份主动技 | 每一种操作都写清是否占角色行动、何时可用、次数上限和结算顺序 |
| 数值预算 | 单人基础token为3，常见身份加2或3，强力卡费用3—5 | 先算整场行动、出牌、敌伤与回复预算，验证强力卡可用条件及免费基础行动是否导致永远不出牌 |
| 共享规则与角色描述 | 共享token、共享窗口；角色稿仍有个人资源或个人窗口措辞 | 以确认后的统一规则为准；角色稿中额外机制拆进卡牌、插件、装备或被动升级 |
| 三选一招募 | 规则要求三名候选；Demo仅制作三名角色且有一人已入队 | 可用候选不足时显示实际人数并保留跳过强化；不复制角色，不为凑三选一扩角色量 |
| 共享血量与热插拔 | 角色下线不受伤，但队伍只有公共token | 明确下线免疫的是定向效果、行动封锁还是公共伤害；验证单人全部下线时敌人如何行动，不能成为无限免伤 |
| 版本与建议的效力 | `_build/src`、Word、审阅建议并存；Muse稿称无立绘，文件夹已有Muse.png | Word和用户修改意见是现有依据，审阅稿是建议而非已采纳事实，构建目录不作权威来源；逐项记录裁决，实查素材 |
| 长度与内容规模 | 六章十一层与30—60分钟目标不一致 | Demo先测短流程，完整版本的层数和时长待真实战斗节奏确定 |
| 对外称呼和素材来源 | 角色索引坚持模型代号；玩法稿要求发行时原创名；美术来源文件指向外部站点 | 记录为发布前决策及素材来源核对事项；不擅自改名，也不把外部参考直接标成原创可发布资产 |

## 提示词的使用方法

建议同一阶段使用一个聊天；新阶段给AI提供本阶段提示词、共同前缀和上阶段产物。能访问项目文件的AI直接读写；不能访问文件的AI需由你提供相关内容，且不得声称已经读写或运行。

以下提示词授权AI完成指定阶段，不自动授权推进后续所有阶段。每阶段完成后，你可以用验收条件检查，再发送下一阶段提示词。

### 每阶段共同前缀

```text
你正在协助推进《算力回廊》，一个以AI娘小队、共享token和提示词窗口为特色的回合制肉鸽卡牌游戏。

项目目录：D:\MyPros\AI游戏。
如有文件访问能力，先检查适用的项目说明和本阶段已有产物，保留用户现有修改。基础资料为《总览.docx》《玩法.docx》《角色设定/性格/00_索引.docx》、相关角色稿、改.txt、改2.txt和《角色设定/性格审阅与轻喜剧调整建议.md》。审阅稿只提供建议，不代表用户已采纳；_build目录是加工材料，不作为规则定稿。后续以docs目录中已确认的规则与决策记录为准；如无确认，明确标记假设，不能伪造用户决定。

目标先做PC短流程Demo。当前阶段以本轮任务范围为限；16名角色、6章是长期方向。AI娘是游戏题材，当前没有接入真实模型API的需求。优先本地可运行，不引入在线推理依赖。

不要只列建议或写“已完成”。请交付本阶段实际文件、数据或程序；能运行则验证。没有文件访问或运行能力时，明确说明限制，提供可保存的完整内容与操作步骤，不编造执行结果。设计建议与已确认规则分开记录。优先直接完成可逆工作；只有会改变核心定位、需要账户或付费、缺少必需输入时才集中询问。不得覆盖原Word和原美术文件，不自行发布、购买、上传或联系他人。

完成时说明：交付位置、验证结果、尚未解决的问题及是否满足阶段验收条件。把关键决定写入docs/决策记录.md，把供下一阶段使用的简短说明写入docs/阶段交接.md。
```

## 阶段一 统一规则与收缩范围

目的：把文档中的构想整理成一份后续制作能遵循的基准，区分必须先决定的问题和可以用测试回答的问题。

交付物：规则基准、Demo范围、决策记录。验收：关键冲突都有出处、建议和处理状态；原型包含什么、暂缓什么可以一眼看清。尚未确认的核心变更不得自动写成定稿。

```text
请作为本项目的制作人兼系统策划，完成规则整理和Demo范围规划，本阶段不写游戏程序。

读取项目基础资料，输出docs/规则基准.md、docs/Demo范围.md和docs/决策记录.md。逐项标记：已有一致规则、现有矛盾、你的建议、待用户决定。引用来源文件和章节，不以文件时间新旧自动裁定优先级。

重点解决：每战回满token与休息回血、token归零立即失败与学生救场、手牌容量与上下文负荷、已使用及未使用卡的去向、牌库耗尽后的玩法、遗忘与角色离线区的区别、各种操作的行动预算、共享token下热插拔的效果、共享窗口下量化如何生效、队伍人数及招募候选不足、角色核心Skill与插件和harness的边界。

给出最小改动的原型默认方案及取舍。不得默默删除token兼生命值、共享窗口、每角色一次行动等现有核心方向。把战斗原型、内部流程版和对外Demo的范围分开；首轮以3名角色为上限，先做单人固定战斗，后续再扩到短章流程。六章、16人、进化与多形态保持在后续清单。

最终给出最多5个需要用户决定的问题，其余可逆事项给默认建议。列出每个版本的验收条件和依赖关系。不能因文档整理继续扩充系统数量。
```

## 阶段二 把规则写成可计算的战斗规格

目的：在制作界面前，通过回合推演发现死循环、无解和资源预算问题。

交付物：战斗规格、第一批数据、回合样例与数值推演。验收：所有操作有合法条件、消耗和去向；至少两套策略有不同取舍，没有“永远普攻”或“无限免费调用”的明显单一解。

```text
请作为战斗系统策划，根据docs/规则基准.md和docs/Demo范围.md，完成可供程序直接实现的单场战斗规格。未确认的核心规则先显式标为原型假设，不能宣称已定稿。

输出docs/战斗规格.md及结构化的角色、身份、卡牌、敌人初版数据。原型只用GPT、一个固定身份、12—16种卡、3种普通敌人模板和一场固定测试战斗；这里的卡牌数量是不同设计的数量，初始牌组的复制张数另行定义。

明确：战斗及回合状态、行动顺序、费用计算、护盾、token归零判定、温度效果、载入容量、上下文负荷、缓存、遗忘、检索、压缩、截断、未用手牌去向和无牌可载入的行为。用卡牌区域流转图或表说明每一种移动。温度先做可解释的低温/高温两档原型，所有数值必须有单位、上下限和触发时点。

按当前单人基础token3加身份带入量，计算整场费用、敌人伤害和回复预算；如需调整数值，列出现值、建议值和理由。手工走通至少3场完整样例，比较保守基础行动、积极出牌和高温爆发。检查免费基础行动是否压倒卡牌、一次强力卡是否必死、开局满手是否直接过载、无牌时是否还能继续。

输出docs/战斗推演.md，保留逐回合明细，注明哪些是手算、哪些经过实际程序验证。本阶段通过的标准是规格能无歧义执行，且至少两种策略存在合理取舍，不是强行给出平衡已完成的结论。
```

## 阶段三 制作能直接玩的单场战斗

目的：尽早得到可操作反馈。先用占位界面验证资源决策，不投入全套动画。

交付物：本地可启动的战斗、运行说明、关键规则验证。验收：能开始、行动、获胜或失败并重开；结算与上一阶段推演一致，玩家看得出费用和危险。

```text
请作为游戏程序员，实现docs/战斗规格.md规定的单场战斗原型。

先检查项目是否已有游戏工程，以及本机可用开发工具。有现成工程就沿用；没有则结合PC本地运行、2D卡牌交互和可导出性选择一种简单方案，记录原因后实施。涉及版本能力、安装步骤或导出限制时核对官方资料，不凭记忆编造。需要下载或付费时按环境要求处理，不擅自安装不必要依赖。

严格限制在GPT、1个固定身份、12—16种卡和固定测试战斗。实现开始、载入、基础行动、出牌、低/高温、上下文负荷、缓存、敌人意图、敌人行动、胜败与重开；检索、压缩等只做规格中已经进入原型范围的操作。不要做地图、角色收集、商店、进化或完整美术。

战斗规则与界面分离，内容尽量数据化。随机行为使用可记录的种子，提供简洁战斗日志。界面应显示当前token及预计消耗、剩余行动、窗口与上下文状态；会因费用导致失败的操作必须清楚提示，不能偷改规则。

提供docs/运行说明.md，以及关键规则的验证结果。优先验证token归零、费用边界、行动重复、满窗口、缓存溢出和牌区流转，避免给所有显示代码堆测试。亲自启动并完成至少一次胜利和一次失败流程；无法交互验证的部分明确列为待人工检查。交付一个可以继续迭代的可玩原型。
```

## 阶段四 加入小队与差异化机制

目的：验证“组队管理AI模型”的特色，控制新增系统数量。

交付物：3名可测试角色、2个身份、编队、有限离线调用、第二轮战斗验证。验收：三人各自可单人完成入门战斗；组队有协同；离线、下线与回归都不会丢卡或无限套利。

```text
请在已有战斗原型上，完成小队战斗验证，不制作地图。

增加Claude和DeepSeek女仆形态，使原型共有3名角色；身份扩为学生和程序员，但只实现已统一的身份规则。每人有独立基础行动、1项核心Skill和一个清楚的玩法特点：GPT验证通才循环，Claude验证公共资源保护，DeepSeek验证蓄力或token效率。具体效果须服从规则基准，不为表现人设新增个人血条或个人窗口。

实现1/2/3人上场、行动顺序、通用与专属牌权限、混合卡组、离线卡处理、有限次算力调用和下回合回归。3名角色足够验证：三人全上场测试行动预算；只上场1—2人，余下角色作为离线队员测试调用。不因测试离线机制临时增加第4名角色。

温度先保留两档，根据原型反馈再决定是否需要连续滑块。插件最多给每人1个简单初始效果；harness、提示词链和协议值暂缓。检查热插拔是否能让单人永久免伤、离线调用是否绕过行动限制、回归是否复制卡牌、免费减费是否形成无限循环。规则未定义的行为先记录方案再实现，不默默补成新系统。

补充结构化角色数据和docs/小队验证.md，覆盖3名角色各自单人开局、双人协同、三人行动、离线调用、暂时下线及回归。交付可玩的更新版本和每个场景的实际结果。若核心战斗仍无取舍，先修战斗，不进入内容扩展。
```

## 阶段五 串通地图和肉鸽循环

目的：从“战斗演示”变成“有开局、有成长、有结尾的一局游戏”。

交付物：一章内部流程、招募和永久解锁、基础存档；通过后扩成两章Demo骨架。验收：能从选人走到结算，重新开局可选刚解锁的角色，存档后能继续。

```text
请基于现有战斗版本，先串通一章约6—8个实际经过节点的内部流程，验收后再扩成两章短流程。

实现选身份、选开局角色、分支地图、战斗、三选一卡牌奖励、少量事件、简化商店、休息、Boss、战后招募或一种跳过强化、编队、结算及再开一局。若仍采用每战回满token，休息只实现已确认的升级或删卡功能，不加入失去作用的回血选项。先用一种跳过强化验证与招募的竞争，不一次实现蒸馏、微调、量化全套。

招募未解锁角色时永久解锁；候选不足3人时显示实际人数，保留跳过强化。测试候选已入队、无可招募角色和队伍不同上场人数。每次招募后展示牌组变化，避免专属牌加入造成无说明的稀释。

单局存档与永久解锁分开保存。支持节点间退出后继续；损坏或旧版本存档要有可理解的恢复处理，不能静默清掉永久进度。随机种子保存，避免读档改变既有节点内容。

内部一章验收通过后扩为两章骨架：第一章Boss后招募，第二章Boss后Demo结算；完整版本仍保留六章方向。用一场小型编队测试覆盖三人上场，不为赶在两章结尾凑齐三人而改变招募节奏。

交付docs/流程验收.md，实际走通成功、失败、招募、跳过强化、重开后选新角色、退出继续及存档恢复。不要把地图可点击当成完整循环已完成。
```

## 阶段六 制作内容与清楚的游戏界面

目的：形成能交给陌生玩家的短篇体验，让角色辨识度服务于战斗理解。

交付物：Demo内容数据、统一视觉规范、必要美术和音效清单、渐进教学。验收：主要画面信息可读，无必须靠开发者口头解释的核心操作；每名角色有可辨认的表现。

```text
请作为游戏内容策划与界面设计协作者，在两章骨架上完成Demo内容与可读性。本阶段不增加角色和大型系统。

内容上限约为3名角色、2个身份、30—40种卡、6种普通敌人模板、2种精英、2个Boss和少量事件；这些是预算上限，不是必须凑满的指标。优先补齐现有构筑缺口。至少一个Boss使用清楚公开的测试条件，并按玩家当前人数可达成；首章单人Boss不能要求两个角色行动或两张牌的未解锁组合。

整理角色、卡牌、敌人、事件、状态和词条的数据表，使用稳定ID，检查引用不存在、重复ID和无法获得的卡。完成最小素材清单、状态图标、卡面信息层级和局内提示。harness如纳入，仅做少量通用装备及Demo角色适用的装备；不为未制作角色做装备池。与插件、Skill的区别要能简短解释。

逐步引导token兼生命值、基础行动、窗口/上下文、缓存、温度与离线调用。展示预计费用、敌人意图、离线原因及可回归时机；关键状态不能只靠颜色区分。先保证鼠标操作、文本大小和提示可读，不把规则日志当正式游戏界面。

基调以科幻轻喜剧为目标。把性格审阅建议作为候选，尊重用户已有改稿，不擅自改变核心人设。每人先做少量战斗短句与一段队友互动，避免反复苦情与单一热梗。新增网络引语或现实产品事实必须验证来源，原创台词明确归为原创。

核对素材清单与真实文件，包括已有Muse.png；美术参考、来源待确认素材与拟发布资产分别标记，不修改原图。没有合适成品就先用占位，不制造已获授权的结论。交付docs/Demo内容清单.md、docs/视觉与交互规范.md及完整可玩更新，并检查主要画面、弹窗、长文本和高低分辨率显示。
```

## 阶段七 试玩和数值迭代

目的：用真实行为判断玩法是否成立，把优化集中在影响理解和选择的问题上。

交付物：试玩包、测试说明、匿名反馈模板、问题清单和一轮修订。验收：关键流程无阻断；玩家理解有所改善；有证据支持下一轮调整。

```text
请作为测试与平衡负责人，为当前Demo安排并执行能力范围内的验证。

先完成程序可做的检查：不同种子与初始角色、地图可达性、奖励及招募边界、卡牌引用、零费用循环、离线权限、读档一致性和胜败结算。需要批量模拟时采用至少两种行为策略，说明策略局限；不要把模拟胜率当成人类体验或已经平衡的证明。

准备docs/试玩说明.md、docs/试玩反馈模板.md和docs/问题与平衡记录.md，供我邀请3—5名未接触设定的玩家试玩，不自行联系任何人。记录首局时长、首次困惑、死亡前操作、基础行动与卡牌使用、温度选择、招募选择和是否愿意再开一局。仅在本地记录必要游戏行为，不收集个人身份信息。

暂定观察目标：多数试玩者不需口头指导即可完成首场战斗，能解释token为何减少；没有卡死、存档丢失或稳定可复现的无限循环；至少观察到两种有理由的资源策略。小样本只用于发现问题，不报告为统计结论。真实反馈未提供时，交付等待填写的表和已执行结果，不能伪造玩家评价。

按阻断流程、规则难理解、策略单一、表现问题排序。每轮只改少数有假设的参数或规则，保留修改前后值、预期影响、实际验证与回退办法。优先解决免费基础行动压倒出牌、高温收益不可感知、招募只稀释卡组、辅助单人无法开局等问题，不用新增系统掩盖旧问题。

完成可自主实施的修复与回归；把必须依赖真实试玩的部分明确留待输入。给出是否进入Demo打包的结论及证据，不把未验证项勾成通过。
```

## 阶段八 打包 Demo 与准备下一轮

交付物：带版本号的本地包、玩家说明、已知问题、发布前待办和下一轮优先级。验收：在干净目录或可用的另一环境完成启动和短流程验证；无法验证的环境明确注明。

```text

冻结本轮范围，整理版本号、构建方法、必要运行依赖、操作说明、存档位置、更新记录与已知问题。尽量让包可以解压后直接运行；确有依赖则给出准确说明。验证新玩家首次启动、默认设置、退出继续、重新开局、胜败结算和永久解锁保留。明确构建成功、实际启动成功、完整流程通过分别是否达成。

输出docs/Demo发布检查.md、docs/玩家说明.md及docs/后续迭代优先级.md。后续计划必须依据试玩证据排序：先稳定性和核心决策，再补内容；新增角色一次只扩1—2人，并验证其单人开局和与已有角色的交互。只有时长与留存动机已有基本证据，才扩大章节或启动完整16人内容制作。
```

## 节奏与投入建议

以下按个人主导、AI辅助、优先完成PC可玩版本估算，仅用于安排投入顺序。尚未确定引擎、开发经验、每日工时与资产制作方式，不能视为交付承诺。阶段内返工和用户反馈可能改变时间。

| 阶段 | 建议首轮投入 | 完成标志 |
| --- | --- | --- |
| 一 规则与范围 | 1—2个工作日 | 重要规则冲突被显式处理，原型边界清楚 |
| 二 战斗规格 | 2—3个工作日 | 完整回合样例走通，费用和牌区无歧义 |
| 三 战斗原型 | 3—5个工作日 | 单场可反复玩，能解释胜负 |
| 四 小队机制 | 3—5个工作日 | 单人、组队、离线调用各自通过验证 |
| 五 肉鸽流程 | 5—8个工作日 | 选人到结算、招募与存档串通 |
| 六 内容与界面 | 5—10个工作日 | 达到陌生玩家可试玩的可读性 |
| 七 试玩迭代 | 5—8个工作日及反馈等待 | 修复有证据支持，阻断问题清零 |
| 八 打包准备 | 2—3个工作日 | 本地包和说明可交付，未验证项清楚 |

合计约26—44个工作日，实际依赖每日投入和返工。首个重要检查点是阶段三结束，预算应先保障这一点。若战斗尚不好玩，缩减内容并返回阶段二或三，而不是按日历强行推进。

## 持续执行的工作习惯

1. 一次让AI完成一个可验收目标。每轮交付都能启动、能阅读或能比较，避免一条提示词要求做完整六章游戏。
2. 规则、数据和程序有明确对应关系。改费用或回复量先改数据；改结算逻辑同时更新规格与决策记录，避免多个文档各自成为定稿。
3. 每次跨阶段保留可回退版本。已有版本控制则使用它，没有则保存带版本号的原型快照。原Word和原美术只作来源，不被脚本批量覆盖。
4. 大批美术、全角色卡组和配音等投入放在核心战斗之后。每轮先补会改善玩家选择的内容。
5. 原型优先本地离线。题材里的AI模型不自动意味着需要接入真实AI API；如未来确有动态对话需求，另立任务验证价值、依赖和运行成本。
6. 每阶段把“还没做”和“做了但没验证”分开写。尤其是界面交互、真实试玩和干净环境启动，不能用代码检查代替。

现在最值得立即执行的是阶段一和阶段二，随后尽快看到第一场可玩战斗。做到阶段三时，再根据体验决定哪些机制值得继续投入。
