## 1. 结论摘要（有立场）

**总体判断：战斗舞台的“构图”已经成立，但“世界”还没建起来。** 布局（角色左、敌人右、下方低占比操作带、右下圆形结束回合）与 README、概念稿一致，卡面压缩干净，地图几乎是全项目唯一 100% 按自己规范落地的界面；但**玩家看到的第一屏（标题）、最后一屏（结算）、以及唯一的叙事承载（剧情弹层）都没有美术**，战场背景仍是一张明确命名为 `paper_arena_placeholder.svg` 的扁平矢量占位图，战斗内同时并存**五种互不相干的渲染语言**（二次元立绘 / 矢量几何背景 / 照片感静物卡图 / 灰纸手绘地图 / 纯色底文字页）。这直接违反总纲“三层不是三种互不相干的画风，共享相同轮廓语言、角色比例和基础色”（`docs/总体视觉风格.md:23`）。

- **值得保留（不要推倒重做）**：战斗舞台的左右对峙构图与操作带占比、卡面“插画窗+卡名+费用”三段结构、地图的低饱和灰纸体系与八类符号方向、三名角色的风格统一与角色色系统、发光预算（实测达标）。
- **必须改（P0）**：①战场背景从占位资产换成正式美术，并让战斗与明线/暗线共享同一轮廓语言；②标题/结算/剧情弹层补上“世界”，同时清掉面向开发者的文案（“Demo 垂直切片”“固定随机种子”“常规/独立测试场”）。
- **必须改（P1）**：卡面零效果信息与同名卡不可区分、归属标记被手牌重叠吃掉、字体体系未落地（无字体资产，10–12px 中文靠系统回退）、状态板 `◇` 无图例且三行格式不统一、战场“红”同时承担四种语义且冷/暖半屏割裂、敌人美术被意图胶囊与血条面板遮掉约 1/4、顶部缺“当前行动者/行动顺序”。

## 2. 问题清单

判定标准：**P0** = 与已确认文档/视觉总纲正面冲突，或直接影响“这是不是一个成品”的判断，必须改；**P1** = 影响信息传达或观感一致性，必须在本次 Demo 内改；**P2** = 打磨项或设计选择，可排期。

### P0

**P0-1 战场背景仍是占位资产，且与角色/敌人不是同一套画风**
- 证据：`game/scripts/main_stage2.gd:10` `const BATTLE_BACKGROUND = preload("res://assets/battle/paper_arena_placeholder.svg")`；该 SVG 全文仍以“placeholder”命名并置入正式战斗（`game/assets/battle/paper_arena_placeholder.svg:18-47`：扁平山体折线、经纬网格、整幅 `#ef6a62` 0→0.35 红渐变）；实机 `_build/evidence/art_review/battle_current.png`；设计目标见 `docs/精细化战斗场景设计方案.md:20-22`（验收态：几何折叠/拉伸/锁死+警示、0/1 粒子、现实物件锚点）、`:252`（四层视差与粒子色系）。
- 现象：角色与敌人是高细节二次元渲染，背景是低多边形纯色矢量，卡面插画又是照片感静物；三者同一帧内并置，玩家能明确感到“素材来自三个项目”。四任务独立战场（城关/站务塔/铁闸/提交版）与四层视差（`docs/Demo视听与表现设计方案.md:180`）均未实现。
- 为何不合理：违反 `docs/总体视觉风格.md:23`（共享轮廓语言）、`:19-21`（战斗=任务世界进入验收态）。这是本次评审里**最大的单点风格断点**，且无法靠调色修好，只能换资产。
- 建议：按“验收态”重绘一张与立绘同笔触的战场底图（折纸城市废墟 + 纸页/表格地形 + 一层中性补光），并保留现有左右分界构图与 UI 安全区（左侧 y<438 角色区、下方 y>492 手牌区）；`paper_arena_placeholder.svg` 只留在测试/降级分支并改名为明确的 debug 资源。

**P0-2 标题画面、结算画面、剧情弹层三处“世界入口/出口”无美术，且暴露开发信息**
- 证据：**现行代码** `game/scripts/main_stage2.gd:575-611`（`_show_title()`）：画面只有 6 个文本节点 + 1 个按钮，**没有任何背景图/美术节点**——`:579` “离线卡牌战术 · Demo 垂直切片”（18px）、`:582` 标题 68px、`:588` 副标题 24px、`:597` “开始新的委托”、`:606` “固定随机种子：%d（可用 --seed=数字 覆盖）”、`:609` “常规：路线图、1–2 人两战与休息 · 独立测试场：三人战斗”。旧截图 `_build/evidence/title.png`（10-25 11:50，比现行代码旧两天，仍写着“Windows 垂直切片”与“本切片：角色选择 → … → 结果”）。结算：`_build/evidence/art_review/result_win_current.png` 与 `result_loss_current.png`（实测 ink 覆盖率仅 5.9% / 5.3%，两态除文案与颜色外完全同构，`main_stage2.gd:2020`）。剧情：`_build/evidence/story_opening_overlay.png`（940×530 深色圆角面板 + 3 行 22px 文字）。
- 现象：总纲要求标题画面是“尚未完全生成的道路：终端车停在近景，远处由纸页、光点和云层共同形成空白终点”（`docs/总体视觉风格.md:244-246`），实机是纯文字页——`title.png` 里那句“本切片流程”虽已在现行代码移除，但“Demo 垂直切片”“固定随机种子”“常规/独立测试场”三条开发口径仍在首屏。结算画面没有结算（无 token 消耗、无任务验收戳、无队伍状态），且缺“验收”这一核心意象——而 `docs/精细化战斗场景设计方案.md:94` 明确写了胜利应盖一枚“准予通过”戳记。
- 为何不合理：首屏决定玩家对“这是不是成品”的判断；把 seed、切片范围写进标题，等于把调试面板当门面。结算只有两行字，20–35 分钟的流程结尾没有回报。
- 建议：标题用现有 `总体视觉基准图_v1.png` 的“未完成道路”构图做一张 1280×720 底图（甚至可先用基准图做裁切/重绘的过渡版），文案收敛为标题 + 一句标语 + 开始按钮；结算画面加“验收戳记动画/静态戳”与本次消耗的 token 摘要；seed 与流程说明移入设置层或调试开关。

### P1

**P1-1 卡面零效果信息，数值只能悬停；费用位置与 README/门禁三方不一致**
- 证据：`_build/evidence/art_review/battle_current.png`（5 张手牌卡面 = 插画窗 + 卡名 + “token N”，无任何数值）；`battle_current_hover.png`（悬停面板才显示“Claude / 防护5”，`main_stage2.gd` 详情面板 248×104 @(516,354)）；`game/tests/test_ui_flows.gd:322-324` 明确**禁止**卡面出现 费用/伤害/归属/白饭/防护/恢复，`:328-330` 禁止旧费用徽标，`:331-346` 要求卡名下方 “token  N”。
- 现象：一张手牌里同时有“标准指令”（攻击 6、费 1）、“防护指令”（防护 4、费 0）、“强力指令”（攻击 10、费 2，见 `game/data/content.json:20-49`），卡面只有名字与费用，伤害/防护数值必须逐张悬停；`docs/Demo视听与表现设计方案.md:265` 设计的“下部 Rule Text 占 24%、关键数字放大 130% 并上色”在实机完全不存在。同时 `game/README.md:5` 与 `docs/迭代记录/阶段交接.md:65`（N48）都写“左上角单个费用数字”，现行代码却移到了卡名下方 12px 的 “token 0”，门禁还反过来禁止徽标——三份材料互相打架。
- 为何不合理：肉鸽卡牌的核心循环是“看牌—选牌”，把全部效果数字推进悬停，等于要求玩家对 5 张牌各悬停一次；同名卡更是失去可读性。README/N48/门禁不一致会导致后续返工。
- 建议：在 132×184 内恢复一行紧凑数值（如“防护 5 / 费用 1”，14px，数字上角色色），把长文案留给悬停；同步修正 README:5 与 N48 记录或门禁断言，二者选一并写清“费用徽标已废”的原因。

**P1-2 专属牌的归属标记被手牌重叠吃掉（三人共享手牌下的核心信息）**
- 证据：`game/scripts/card_art.gd:253-265`（标记圆心 `Vector2(size.x - 18, 18)`、半径 11，即落在卡右手边 22px 内）；`main_stage2.gd:23`（卡宽 132）、`:1263` 附近 `spacing = 106` → 相邻卡重叠 26px；`battle_current.png` 卡 1–4 的标记只露出约 1/3，`battle_current_hover.png` 抬升后完整。
- 现象：卡 1“最小改动”右上角的深色小圆只露出一段橙弧，远看像脏点；玩家无法在默认手牌姿态下读出“这张是 Claude 专属”。
- 为何不合理：`docs/UI与战斗美术重构方案.md:47` 要求“专属牌用角色色归属签片 + 小型角色徽记”；共享手牌机制里归属是出牌决策依据。现在实际能读出的只有卡框描边色与 token 行颜色，标记本身失效。
- 建议：标记移到卡面左上角插画窗内（不被重叠区覆盖），或把间距从 106 提到 112–116 并缩小标记半径；也可改为卡名左侧的角色色小色块（不依赖右下角空间）。

**P1-3 字体体系没有落地：无字体资产、无主题，中文与拉丁/数字混排**
- 证据：`game/assets` 下无任何 `.ttf/.otf/.theme/.tres`；`game/project.godot` 全文（26 行）无 `[gui]`/theme 配置；`main_stage2.gd` 只有字号覆盖（`:629`、`:905`、`:1287`、`:2193`、`:2200`、`:2211`），无字体族覆盖；状态板字号实测为 名称 13px（`:1133`）、TOKEN 12px（`:1137`）、被动行 **10px**（`:1142`）。实机 `crops/cur_plates_3x.png` 中同一条 “TOKEN 12/12　◇ 0” 的拉丁数字与下一行中文“连击 0 / 2”字形风格明显不同。
- 现象：中文由系统回退字体渲染（黑体类），拉丁/数字来自引擎默认字体，同界面两套字形；状态板第三行 10–11px、token 行 12px、卡名下方 token 11–12px，在 1280×720 下中文笔画已发糊。
- 为何不合理：`docs/总体视觉风格.md:219` 要求“一套清晰的人文无衬线体 + 一套等宽数字体（只用于 token/版本号/01 碎片）”，`:253` 要求 1080p 下正文不低于基准字号。当前既无字体一致性，也无字号下限，换一台机器字形还会变。
- 建议：打包 1 套中文字体（SIL 授权的思源黑体/OFL 字体）+ 1 套等宽数字体，在 `project.godot` 的 `[gui]` 里设为默认；把 10–11px 的状态三行提到 12px（必要时缩文案，如“连击 0/2”→“0/2”加图标）。

**P1-4 状态板 `◇` 无图例，三名角色第三行格式不统一**
- 证据：`main_stage2.gd:1137` `_label("TOKEN %d/%d　 ◇ %d" % [token, max, actor["shield"]], 12, …)`（`◇` 即防护值，全项目无图例说明）；`:2121-2126` `_passive_status()`：GPT “连击 %d / 2”、Claude “反击：就绪（+4）/未就绪”、DeepSeek “白饭 %d / 3”。实机 `battle_current.png`、`crops/cur_plates_3x.png`。
- 现象：同一块状态板三行分别是“名称 / TOKEN 12/12 ◇ 0 / 被动”，第三行有的用冒号加文字（反击：未就绪），有的用斜杠分数（连击 0 / 2），空格位置也不一致；`◇` 是唯一不解释的符号，而它代表的是**能挡多少伤害**这种关键数值。
- 为何不合理：`docs/总体视觉风格.md:280` 要求“去掉文字仍能分辨状态”，`:253` 要求发光/符号背后有可读衬底；现在防护反而比 token 更隐晦，与“token 是唯一资源”的玩法重心相反。
- 建议：`◇` 换成有语义的盾形小图标 + 数字，或在首回合加一次图例；三行统一为“名称 / 资源 + 资源 / 被动（就绪/未就绪用图形）”，三行宽度对齐。

**P1-5 战场“红”同时承担四种语义，冷/暖半屏割裂；发光预算虽达标但观感仍是“两块海报拼在一起”**
- 证据：实测 `battle_current.png` 红主导像素 **6.4%**（≤15% 上限，`docs/Demo视听与表现设计方案.md:27`、`docs/总体视觉风格.md:50`），近白像素 12.1%；但背景 SVG `paper_arena_placeholder.svg:41` 用一整块 538×720（**占画面 42%**）的 `#ef6a62` 渐变铺满右半屏，`:45-46` 再叠两条红弧，`battle_ui_decor.gd:33-47` 又叠右半屏红层与 5 条红色 fracture 线；敌人本体再发红光。
- 现象：左半屏是 #dfeef0→#96bdc5 的浅灰青，右半屏是深红，中间几乎没有过渡；红色同时表示“敌方地形/敌人/危险警示/受伤”，任务主色缺失。
- 为何不合理：`docs/总体视觉风格.md:50` 规定同区域“一个任务主色 + 一个角色强调色 + 一个系统状态色”，当前是两色硬切且红被复用四义。**实测说明 15% 这条数值规则被满足了，但满足了也没解决观感问题**——所以真正需要补的约束是“单场景一个主色 + 红只保留一种含义”，而不是继续压发光面积。
- 建议：把右半屏红降为“局部警示几何”（fracture 线 + 敌人轮廓光），背景改任务主色（纸页暖白/木色），红色只留给“意图/伤害”；左右用一条纸页撕裂带过渡而非 42% 色块。

**P1-6 敌人美术被意图胶囊与血条面板遮掉约 1/4；Boss 与普通敌人无体量差**
- 证据：`main_stage2.gd:1189-1191` 意图胶囊 `(1006,60) 160×68`、`:1198` 敌人面板 `(805,365)`（实测约 380×64，名 17px、血条 342×10）；敌人容器 `(788,64) 405×350`（`:1163-1167`）。实机 `battle_current.png`：胶囊压住敌人右上纸页，面板压住敌人下半身；`ui_boss_battle_v6.png` 中“本次提交版 30/30”与普通敌人同尺寸、同“纸页+红核”剪影。
- 现象：敌人是画面唯一的“对手”，但两块 UI 正好落在它的头肩与胸口；Boss 只是换了贴图，没有 `docs/Demo视听与表现设计方案.md:100` 要求的“巍峨的单页折纸塔 + 幕布 + 金属验讫公章”体量感，玩家感受不到“最终提交”。
- 建议：意图胶囊移到敌人上方安全区（y<40）或左侧空白带，血条面板下移到 y≈400 的纸面带上；Boss 单独放大到 1.3–1.5 倍并换竖构图，让“公章”进入画面。

**P1-7 顶部缺“当前行动者 / 行动顺序”的显式信息**
- 证据：`battle_ui_decor.gd:5-7` 注释明确“Turn banners and fake reticles were removed”；实机 `battle_current.png` 顶部只有左上“第 1 回合”、右上“Ⅱ”暂停、右上意图胶囊；当前行动者只靠角色板块描边 + 头顶“▼”（`main_stage2.gd:1148-1155`）。对照 `docs/美术/UI战斗概念图_三人共享手牌_v2.png` 顶栏（回合 1 + 菱形进度轨 + 右侧图标栏）与 `docs/迭代记录/Demo正式分层美术与UI定稿.md:29-35`（Y0–54 需含行动顺序与当前行动者）。
- 现象：三人各自有 token、共享手牌，但界面不告诉玩家“现在轮到谁 / 谁的 token 会被扣”。截图里 GPT 板块有蓝框和 ▼，但是否“可切换”没有任何提示——规则只写在角色板块的 tooltip 里（`:1100` `"%s｜点击切换当前行动角色；把牌拖到角色身上即可释放"`），鼠标移上去才知道。
- 建议：在回合标题右侧加一行低对比文字“当前：GPT（其余 2 人待行动）”+ 三枚角色色小圆点表示顺序；或恢复概念稿的菱形进度轨（只保留 3 个节点，不造假数据）。

## 3. 优点清单（建议保留）

1. **舞台构图成立**：左三人前后错落（`main_stage2.gd:1117-1127` 每名角色 158×230 立绘 + 162×64 状态板，站位比例沿用 `docs/迭代记录/Demo正式分层美术与UI定稿.md:15-25`）、右侧 405×350 放大的敌人、下方 y=492 起、高 228px（占屏 32%）的低占比操作带、右下 62×62 圆形“↑”结束回合、左上只留“第 N 回合”——与 `README.md:5` 和概念稿一致，比 v6 的整宽“结束回合”更接近《杀戮尖塔》舞台感。
2. **卡面三段压缩干净**：132×184 内插画窗 120×108 + 卡名 16px + 费用行 12px，卡名 `#111827` on `#f2efe7` 对比约 14:1；5 张扇形 rotation ±3.6°、重叠 26px，确实做出“手里捏着几张牌”的感觉（`_build/evidence/art_review/battle_current.png`）。
3. **地图是唯一像素级按规范落地的界面**：底色/纸色/墨色与 v2 文档完全一致，三节点（普通战/可选休息/终点验收）、虚线椭圆、图例、可选圈双弧+对勾、72px 点击区（`map_route_canvas.gd:206-240`、`地图路线与事件符号_v2.md:39-44`），对比度 6.98:1，符号承担类型、颜色不承担语义（`:49`）——这条“非颜色语义”做得比战斗界面好。
4. **三名角色风格统一、辨识度高**：白/紫、橙/象牙、蓝/青三套配色在立绘、状态板、卡框、token 行上保持一致（`main_stage2.gd:35-37`），一眼能分出 GPT/Claude/DeepSeek。
5. **发光预算达标**：红主导像素 6.4%、近白 12.1%，未突破 15% 上限；敌人红光集中在核心，没有满屏霓虹。
6. **悬停详情不挡手牌**：详情面板固定在敌我空白带 (516,354)、248×104，且悬停牌上抬并描角色色边，交互反馈清楚。
7. **剧情弹层可读性最好**：正文 22px、对比 16.5:1、分页计数与“跳过演出/继续”位置稳定，横向留白舒服。
8. **资产复用有意识**：`card_art.gd` 无插画时走程序化矢量 fallback（攻击/防护/治疗/转移 + 三角色专属），证明卡面结构可以脱离插画独立成立。
