### 1.6 玩家可见层的 3 处数据损坏（实测，非推测）

以下均用 `scripts/story_db.gd` 的 `compose_event`（即运行时唯一入口）实跑得出，证据见 `_build/review/findings/lead-evidence-compose-pages.log`。

**(1) Markdown 标题被当剧情正文**（52 处；其中 12 处在现行可达流程）
`_build/story_drafts/*.md` 每个事件末尾的下一事件标题被拼装器塞进上一个事件最后一段（`{kind:"text"}`），导出后原样进 `story.json`。`_append_all` 不区分 `kind`，把所有非空 text 都追加成页。实测：
```
ch1.student.B1        → 6 页，末页 [fixed] (旁白) ### N2 核对 · 42 与 47
ch1.student.boss      → 10 页，末页 [fixed] (旁白) ### 成功 · 一页
ch1.report.student.acceptFail → 末页 [scene] (分支) ### 章末 · 学生版
```
分布：整库 127 条标题 text 泄漏，其中 **52 条会被渲染**（fixed 15 / scene 28 / branch 9），且不泄漏的 `main`/`partner`/`closing` 段只是"恰好"因走 `_append_speaker_line` 才逃过。

**(2) 分支段的设计口径被当台词念出来**（可达）
```
ch1.report.student.acceptFail → [scene] (分支) 补一封更正说明，写清示例行来源、把缺失项标出来，可补 work_value；不授予其他事实。
```
`work_value` 是内部事实 key，本不该出现在玩家文本里。employee 同构。

**(3) ending 双分支被线性连播，且分支标签被当说话人**（不可达但已在数据里）
```
ch2.student.ending.eligible → 11 页，其中
  [scene] (亲自回复) 屏幕微光荡漾，光点在键盘上方凝聚成一只迟疑的手。
  [scene] (先保留)  表单收进夹层，资格妥善留存，等待下一次由心而发的抉择。
```
两个互斥选项同时播放，说话人是"亲自回复"/"先保留"——不属于创作基准 §8.3 允许的角色名单。且该事件 `staging` 被丢弃。

> 这三处说明：**演出层开工前，数据层必须先修**。否则 A 方案换的皮肤会把坏文本包装得更醒目。

## 2 《剧情演出方式设计方案》v0.1 评审

### 2.1 判定：需修订后批准

**骨架正确，可直接作为实施骨架保留**：

- **S1 工期口径错配**：P0 按全量 reality 估工，但首章 Demo 只 6 个可达；反过来 C 的数据工时被低估（20 个事件 × 4–6 beat 全手写）。
